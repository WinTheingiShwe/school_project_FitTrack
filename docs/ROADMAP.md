# FitTrack 開発ロードマップ

## 目的と現在地

体重・運動・食事を記録し、蓄積したデータから自分の変化を確認できるアプリを目指す。
「データを保存できる」段階から、「ユーザーごとに管理する」「分析して理解する」段階へ進める。

既存のコミットでは、ネイティブPHPへの移行、DB設計、画面構成、体重の登録・履歴・編集までを実装した。
後続の機能はローカルで実装が進んでいるが、機能単位のレビューと公開を終えるまでは未完了として扱う。
投稿日は固定せず、必要な変更と動作確認がそろった単位で公開する。

## 分析で重視する設計

- 体重の7日移動平均は、当日と直前6日間の測定値を対象にし、月をまたぐデータも含める。
- 測定のない日を0kgとして計算しない。移動平均には少なくとも2件の測定を必要とする。
- 運動日数とセッション数を区別し、時間未入力のセッションを平均時間の分母に入れない。
- タンパク質が未入力の食事を含む日は、不完全な日計として扱う。
- 記録率の分母から未来の日を除外し、進行中の月と完了した月の比較には注記を付ける。

現在のローカル版では、計算テスト、PHP・JavaScriptの構文確認、ローカルDBを使った
ダッシュボードHTMLとJSONの生成確認を実施済み。ブラウザ上の表示確認は未実施。
分析機能を公開する際は、対応するテストも同じ変更に含める。

## アカウント機能の検証記録

- 登録時のパスワードハッシュ保存、ログイン時のセッションID更新を確認。
- 未ログイン・削除済みアカウントによるプロフィールへのアクセス拒否を確認。
- 2つのテストアカウントで、送信されたユーザーIDを変更しても他人の目標を更新できないことを確認。
- CSRFトークンなしのプロフィール更新・ログアウトを拒否。
- 体重の入力範囲を既存DBの `DECIMAL(5,2)` に合わせ、存在しない日付や長すぎる名前を拒否。
- テストは一時的なDBスキーマとセッション領域で実施し、終了後に削除。
- ブラウザの表示検証は未実施。ログイン試行制限・パスワード再設定・メール確認は今後の課題。

今回のログイン後の遷移先はプロフィール。既存の体重画面の認証連携は段階2で扱い、
後続機能へのメニューは、その機能を公開するときに追加する。

## 各変更で残す説明

コミットまたはPRには、以下の内容を短く記載する。

1. **課題**：変更前に何が不足していたか。
2. **変更**：ユーザーが何をできるようになったか。
3. **設計理由**：採用した方法と、その理由。理由を確認できない過去の判断は推測で書かない。
4. **確認**：実施したチェックと結果。未確認の内容も明記する。
5. **次の課題**：残る制限と次の改善。

例：個人別の体重管理

> 初期版では体重記録のユーザーIDが固定されていた。ログイン中のユーザーIDを用いた
> 保存・取得・更新へ変更する。公開前に、2つのテストアカウントで記録が分離されることを確認する。

この例は変更の説明方針であり、確認完了の報告ではない。

## 公開時の更新

- 該当する機能と依存ファイルだけをコミットし、別の機能を混ぜない。
- 完了した段階にコミットまたはPRの参照を追加し、READMEの状態も更新する。
- スクリーンショットはデモ用データで撮影し、実装済み画面だけを掲載する。
- 既存の履歴を起点に積み上げ、日付や開発経緯を作り直さない。
- 一連の機能が確認できた時点で、リリースノートに成果と既知の制限をまとめる。
